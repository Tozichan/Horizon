### [Anthropic 称 Claude 参与解决两个黑洞物理开放问题](https://www.anthropic.com/research/claude-black-hole-physics) ⭐️ 8.0/10

Anthropic 发布研究博客，称 Claude 参与解决了黑洞物理中的两个开放问题，并附有相关论文链接。据社区评论转述，其中一项结果给出了与给定中心电荷相容的黑洞质量上限，另一项被描述为复杂且易出错的计算。Anthropic 在公告中明确表示，两项结果都不直接描述我们所在的宇宙，也没有实际应用，只是服务于量子力学与广义相对论如何统一的长期理论研究。目前没有独立验证表明这些结果由 Claude 自主完成，博客与论文中均未出现“prompt”一词，具体提示方式不明。

hackernews · cybermango · 11月19日 17:30 · [社区讨论](https://news.ycombinator.com/item?id=50563148)

**「背景」** Anthropic 在 11 月 17 日的 Claude Fable 5.2 发布中，将“解决黑洞物理两个开放问题”列为一项要点。据外部报道，这两项工作分别涉及自 2003 年以来未完成的 Hawking-Page 相变计算，以及物理学家此前只能通过数值方法猜测的 modular bootstrap 界；研究过程包含多智能体运行与 Lean 形式化检查，并附有预印本链接。

**「影响与争议」** 对关注 AI 辅助理论研究的读者而言，这一案例的价值在于展示大模型参与高难度推导，而非可直接使用的软件或工程成果；由于结果被明确标注为无实际应用，且提示细节缺失，其他研究者难以复现或评估 Claude 的实际贡献比例。

**「社区讨论」** 有评论者认为“Claude 解决了”这一说法反映了对机器的不当拟人化，类比“它逃出了沙箱”与“我们没建好沙箱”，并指出博客和两篇论文中都没有出现“prompt”一词。另一位评论者称，第二项结果——证明与给定中心电荷相容的黑洞质量上限——更有意思，因为任何预测超过该上限的理论都不能作为该宇宙的量子引力理论；也有人指出，该结果并不直接描述我们的宇宙，也无实际应用。还有评论提到，讨论区大量留言并未真正涉及论文本身。

### [OpenJDK PR 披露“java4shell”漏洞报告与 Oracle 接管经过](https://github.com/openjdk/jdk/pull/32781) ⭐️ 8.0/10

Hacker News 上围绕 OpenJDK 的一个拉取请求（PR \#32781）展开讨论，该 PR 涉及一份被称作“java4shell”的 Java 漏洞报告。据评论引用的 adoptium-support 议题 \#1480，PR 作者称 10 月 1 日收到 Oracle 邮件要求其在获得批准前不要推进 PR，10 月 28 日则表示该问题已由 Oracle 接管、己方无需再做任何事。评论还指出，Oracle 在合并提交中的说明与该 PR 中的措辞逐字相同。目前提交本身缺少技术细节，漏洞的具体影响范围与修复状态尚未在材料中得到独立确认。

hackernews · notmine1337 · 11月19日 11:47 · [社区讨论](https://news.ycombinator.com/item?id=50558906)

**「背景」** 该 PR 讨论指向的漏洞是 OpenJDK 中 Base64 解码器的内存破坏问题，编号 CVE-2026-114938，由安全公司 Calif 命名为“Java4Shell”。据 Sophos 与 Palo Alto Networks 的公告，该漏洞于 2026 年 11 月 17 日公开披露，位于 x86-64 处理器上使用的优化 Base64 解码实现中；Oracle 给出的 CVSS 3.1 评分为 8.1（高危），而报告方按 CVSS 4.0 评为 9.2（严重）。Salesforce 的分析指出，该缺陷属于越界写入，可能导致未认证的远程代码执行或内存泄露。

**「社区讨论」** 评论者争论该发现是否真正独立：wood\_spirit 和 darkamaul 提出，协助加州研究人员的 LLM 可能读取过此前的公开议题或 PR，而非独立发现；dlor 则称自己在披露前独立发现并向 Oracle 报告，其测试工具无网络访问，但无法排除相关内容存在于训练数据中。darkamaul 同时认为，判断漏洞严重性并构建利用链仍需人工监督。

### [PHP 流包装器大小写漏洞静默关闭 TLS](https://x.com/ljachowicz/status/2123477025268924514) ⭐️ 8.0/10

PHP 的 HTTP/FTP 流包装器在识别 URL scheme 时不分大小写，但仅在第五个字符为小写 s 时才启用 TLS，导致 HTTPS://、httpS://、FTPS:// 等写法被当作明文 HTTP/FTP 发送，令牌、Basic 认证、Cookie、POST 请求体和 FTP 登录信息可能以明文暴露，被第三方重定向到此类地址时同样受影响。该问题编号为 CVE-2026-128064（GHSA-f6gg-rchx-xw8j），CVSS 4.0 评分 8.2，已在 PHP 8.2.36、8.3.37、8.4.28、8.5.13 和 8.6.0 中修复。8.1 及更早版本已 EOL，不会获得修复，只能自行将 URL 的 scheme 统一转为小写。上述信息来自一条社交媒体转述，尚未见独立验证。

telegram · zaihuapd · 11月20日 03:04

**「背景」** PHP 的 HTTP 与 FTP 流包装器在识别 URL scheme 时不区分大小写，但据 CVE-2026-128064 的描述，只有在固定位置出现小写字母“s”时才启用 TLS，因此大小写混写的 HTTPS、FTPS 地址会被当作明文协议处理。这一行为长期存在，直到本次披露才被公开记录为漏洞。

**「影响与应对」** 使用受影响 PHP 版本发起 HTTPS 或 FTPS 请求的应用，若 URL 的 scheme 含大写字母，连接会静默降级为明文，凭据和请求内容可能泄露。运行 8.2 至 8.6 的用户应升级到对应修复版本；仍在使用 8.1 及更早版本的用户需在代码中统一将 scheme 转为小写作为缓解措施。
