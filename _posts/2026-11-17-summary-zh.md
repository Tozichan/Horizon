### [山东大学团队称获哥德巴赫猜想首个条件性证明](https://mrc.sdu.edu.cn/info/1018/2193.htm) ⭐️ 9.0/10

山东大学李嘉民、刘建亚在论文中声称，在狄利克雷 L 函数广义黎曼猜想（GRH）成立、并满足两种附加谱假设之一的条件下，可以证明所有充分大的偶数都是两个素数之和，且这两个素数位于该偶数的三分之一至三分之二之间。论文称这是首个覆盖所有充分大偶数的二元哥德巴赫猜想条件性证明，但明确表示这并非无条件证明，单靠广义黎曼猜想也不足以推出结论。论文还称所用方法不同于经典的筛法和圆法。该结果目前属于团队声明，尚未见到独立验证。

telegram · zaihuapd · 11月16日 16:01

**「背景」** 哥德巴赫猜想断言每个大于 2 的偶数都可写成两个素数之和，至今未被证明。广义黎曼猜想（GRH）是黎曼猜想在狄利克雷 L 函数上的推广，本身也尚未解决；据检索到的资料，此前已有在 GRH 等显式假设下得到的条件性结果，但均未证明二元哥德巴赫猜想本身。

**「影响与限制」** 这一结果的意义取决于两项附加谱假设能否被接受或验证：在假设成立的前提下，它把二元哥德巴赫猜想的覆盖范围推进到所有充分大偶数，并给出了素数落点的区间约束；但它不构成无条件证明，也不能仅凭广义黎曼猜想推出。对研究者的直接含义是，后续工作需要检验这两条谱假设的合理性，或寻找绕开它们的论证路径。

### [Jiff 1.0：burntsushi 发布 Rust 日期时间库](https://burntsushi.net/jiff/) ⭐️ 8.0/10

burntsushi 发布了 Rust 日期时间库 Jiff 的 1.0 版本，并在项目页面上说明 Jiff 并非在所有场景下都是合适的选择。该版本在 Hacker News 上引发关注，讨论集中在 API 设计与生态采用上。目前没有更多关于具体 API、性能数据或与 chrono 兼容性的细节可供核实。

hackernews · burntsushi · 11月16日 16:53 · [社区讨论](https://news.ycombinator.com/item?id=50519744)

**「背景」** Jiff 是 Andrew Gallant（burntsushi）开发的 Rust 日期时间库，其设计目标是让开发者“跳进成功之坑”，即通过 API 设计引导正确用法。该库提供若干 crate 特性，用于定制对 Rust 标准库、serde 的支持，以及是否将时区数据库副本嵌入二进制文件。在 Jiff 之前，chrono 长期是 Rust 生态中主流的日期时间库；一位曾维护 chrono 约五年的社区成员在讨论中表示，chrono 的 API 稳定性既是用户依赖它的原因，也使改进举步维艰。

**「影响」** 对 Rust 开发者而言，Jiff 1.0 提供了一个新的日期时间库选项，但社区评论显示其能否被更广泛生态采用仍待观察；有评论者希望它逐步取代 chrono。

**「社区讨论」** 曾维护 chrono 约五年的 quodlibetor 表示，他接手维护正是因为不满其 API，但用户更看重 API 稳定，任何改进尝试都遭遇阻力，最终因倦怠而放弃，并对 burntsushi 编写该库表示感谢。Dagonfly 则赞赏项目明确承认自己并非适用于所有场景，认为这是专业工程态度。

### [Optimizely 被入侵，Zoom、GitLab 等网站被植入恶意脚本](https://blog.report-uri.com/worlds-largest-brands-infected-with-malware-via-optimizely/) ⭐️ 8.0/10

据安全博客 Report-URI 报道，Optimizely 疑似遭到供应链攻击，其 CDN 向包括 Zoom、CNN、Fox News、BBC、Salesforce 和 GitLab 在内的多个热门网站投放了恶意 JavaScript。这些脚本被描述为用于窃取加密货币和支付信息，并利用 iOS 设备漏洞。报道明确指出，这不是 CDN 缓存投毒：Optimizely 的 CDN 只是原样分发了被写入的内容，攻击者如何获得对多个互不相关客户项目的写入权限（是系统被攻破、凭据泄露还是其他原因）仍不清楚，需由 Optimizely 解释。上述细节来自报道摘要，尚未见独立验证。

hackernews · kristjansson · 11月16日 23:00 · [社区讨论](https://news.ycombinator.com/item?id=50524767)

**「背景」** Optimizely Web 的运作方式是让每个客户在页面上加载来自 cdn.optimizely.com 的 JavaScript“代码片段”，该文件包含 Optimizely 自身代码、客户的实验配置以及一个可选的 Project JavaScript 字段。此次事件中，恶意代码正是通过这一受信任的第三方脚本进入各站点，且由 Optimizely 自有 CDN 以有效证书提供，因此受影响公司的服务器本身并未显示被入侵。

**「影响与应对」** 使用 Optimizely 脚本的网站运营方应尽快核查其页面加载的第三方代码，并评估是否需要在事件原因查明前暂停或限制该脚本。评论者指出，大型站点本可采用分阶段发布、冷却期和自动安全检查来降低此类风险，但报道未说明 Optimizely 是否已采取这些措施或发布修复。

**「社区讨论」** 有评论者认为，Google Tag Manager 这类让市场部门无需工程介入即可加标签的设计，正是新闻页面加载大量 JavaScript 的根源，希望业界重新评估。也有人批评问责缺失，认为 Optimizely 和 CNN、BBC 等大站都应设置发布冷却、分阶段上线和安全检查，大站甚至应自行托管（vendoring）第三方脚本。另有评论者质疑：若这些网站并不在同一页面处理加密货币或信用卡，恶意脚本为何仍能造成所述危害，是否还存在浏览器安全漏洞。

### [研究：美国超大规模数据中心耗电量超过中等国家](https://www.theverge.com/ai-artificial-intelligence/1034668/data-centers-electricity-climate-pollution-study-harvard) ⭐️ 7.0/10

《Nature Sustainability》发表的一项研究显示，美国超大规模数据中心的主要电力来源仍是化石燃料，其总耗电量可能超过许多国家，并由此产生可观的温室气体排放。研究聚焦于占地数百万平方英尺、主要为支持生成式 AI 而兴建的大型设施，作者认为削减 AI 依赖化石燃料带来的污染仍有大量工作要做。报道未给出具体耗电量或排放数字，因此无法据此评估确切规模。

rss · The Verge · 11月16日 20:27

**「研究背景」** 该研究发表于《Nature Sustainability》，聚焦的是超大规模（hyperscale）数据中心——即占地数百万平方英尺、当前主要为支撑生成式 AI 而大规模兴建的大型设施。据《卫报》报道，研究利用联邦政府数据统计了截至 2025 年 4 月的一年内这些设施的排放，研究者称这一估算几乎肯定是保守值；《纽约时报》则指出，在全部 403 座设施中，54% 的电力来自燃烧化石燃料，以天然气和煤炭为主。

**「对运营方与选址的影响」** 该研究以设施级发电与排放数据为基础，对全美 403 座超大规模数据中心进行归因核算，估算其用电对应约 2570 万吨二氧化碳排放，规模与丹麦相当。这意味着依赖这些设施承载生成式 AI 负载的企业，其算力扩张的碳成本正被逐设施量化，选址所在电网的电源结构将直接影响可报告的排放结果。
